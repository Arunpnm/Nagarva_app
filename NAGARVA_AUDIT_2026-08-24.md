## 1. Executive summary

The platform's **security foundation is in good shape**. RLS is enabled on all 128 tables in the production schema, all 120 tenant-scoped tables are covered, and anonymous direct table access is provably blocked while the intended public resolvers work.

Three things are wrong, in descending order of seriousness:

1. **The APC personal Supabase project has no RLS at all** on 27 tables holding 1,091 rows of real customer data. This is the single largest exposure in the estate and it is not new — it has been known and deferred.
2. **Two of your four public customer-facing pages cannot work**, for two different reasons. `/track` is blocked by a permission grant. `/quote` has no data to resolve against.
3. **The database has no reproducible migration history.** 128 tables exist; the migration ledger has 2 rows.

Nothing here is a schema-design problem. The build quality is sound. These are wiring, grant, and process gaps.

## 2. The live bug you reported

You reported that the quotation link and the sign link shared with a customer are not working. These are **two separate defects with two separate causes.** Treating them as one problem will waste a debugging session.

### 2.1 The `/sign` link — the database is fine, so the page is the problem

I called the public resolver as the `anon` role, using the token generated by your own test today:

```
public_get_signature_request('05399b5e…')
  → {"ok": true,
     "document_id": "NGV-1012",
     "customer_name": "Revathi Kumar",
     "document_type": "invoice"}
```

That row is `pending`, created 24 Aug 00:23 UTC, and does not expire until 7 September. The token is 48 characters. The resolver returns cleanly. **The database is not what is failing.**

The likely cause is a name collision. Two parallel families of these functions exist in the schema, and only one is reachable by an anonymous browser:

| Function | `anon` can execute? | Verified result |
|---|---|---|
| `public_get_signature_request(text)` | ✅ Yes | Returns valid payload |
| `get_signature_request(text)` | ❌ No | `42501 permission denied` |
| `public_submit_signature(text,text,text)` | ✅ Yes | Grant confirmed (not called — it writes) |
| `submit_signature(text,text,text,text)` | ❌ No | service_role only |

**Hypothesis (needs repo confirmation):** the deployed `/sign` page calls `get_signature_request` rather than `public_get_signature_request`. This failure mode is invisible in your own testing because you are authenticated when you test from the app, and the customer is not.

### 2.2 The `/quote` link — nothing was written to resolve against

The resolver works. I called it as `anon` and it returned a row. The problem is upstream.

- The newest row in `public.quotations` is dated **12 August 2026**.
- Your test today created a `document_signatures` row (invoice `NGV-1012`, 00:23 UTC).
- **No `quotations` row was created today at all.**

So whatever token was embedded in the link you shared has no matching row. `get_quotation_by_token` returns zero rows, and the page renders as not-found even though every function in the chain is healthy.

**Two candidate causes, both repo-side:**
- The app writes the quote somewhere other than `public.quotations` (e.g. onto `orders`), while the link-builder points at `quotations`
- The row is written but `token` is not persisted

Supporting evidence for the second: quotation `4f469e3b` (Deepak Sharma, 26 Jul) has `status = 'sent'` but `token IS NULL`. A quote marked as sent with no token is a share link that could never have worked. Token generation is not guaranteed on send. **(F12)**

### 2.3 The 30-second confirmation

Open the failing link in Chrome → F12 → Network → reload. Read the failing request:

| Response | Meaning | Fix |
|---|---|---|
| `403` / `401` | Wrong function family (§2.1) | Rename the call site |
| `404` | Function name does not exist | Rename the call site |
| `200` with `[]` or `{"ok":false}` | Row genuinely absent (§2.2) | Fix the write path |

Send me the request URL and status code and the ambiguity disappears.

### 2.4 `/track` is broken regardless — no ambiguity

`get_order_tracking(p_token text)` is granted to `service_role` **only**. I confirmed the failure directly:

```
get_order_tracking('x') as anon → 42501 permission denied
```

No browser can call this. There is no version of the page that works until either the grant is widened or a `public_`-prefixed sibling is created. Unlike the other two, this needs no further diagnosis. **(F2)**

## 3. Security findings

### F1 — CRITICAL: APC personal project has no RLS

Project `xwnvhrecgubikloxkiis` ("Arunpkrs v3", ap-northeast-1):

| Metric | Value |
|---|---|
| Tables in `public` | 27 |
| Tables with RLS enabled | **0** |
| Live rows | **1,091** |

This is the app in daily business use, holding real customer names, phone numbers, and addresses. With RLS disabled on every table, anyone holding the anon key — which by design ships inside the client application — can read all 1,091 rows.

This has been flagged before and deliberately left alone. That was a defensible call while it was a private single-tenant tool. It stops being defensible the moment Nagarva markets itself to other businesses on data-handling grounds, and it is a DPDP exposure independent of Nagarva entirely.

**It does not need to be fixed this week. It needs a decision and a date, not another deferral.**

### F4 — HIGH: duplicate function families

Two generations of public-page RPCs coexist:

| Generation | Functions | anon grant |
|---|---|---|
| Newer (`public_` prefix) | `public_get_survey`, `public_submit_survey`, `public_get_signature_request`, `public_submit_signature` | ✅ granted |
| Older (bare name) | `get_survey_by_token`, `submit_survey`, `get_signature_request`, `submit_signature`, `get_order_tracking` | mixed |

Note the inconsistency inside the older generation itself: `get_survey_by_token` and `submit_survey` **are** anon-granted, while `get_signature_request` and `get_order_tracking` are not. There is no rule here, only history.

This is the root cause behind §2.1 and §2.4. Until one generation is dropped, the same class of bug will recur every time a page is touched.

**Recommendation:** pick the `public_` generation as canonical, add `public_get_order_tracking`, then `DROP` the older siblings once call sites are confirmed migrated. Do not merely revoke — a dropped function fails loudly at deploy time, a revoked one fails silently in a customer's browser.

### F5 — MEDIUM: QA Edge Functions still deployed to production

| Function | JWT | Concern |
|---|---|---|
| `zzz-claude-qa-mint-session` | verify_jwt: true | **Mints auth sessions.** Test scaffolding, live in production. |
| `qa-generate-auth-link` | verify_jwt: true | Generates auth links. Same category. |

Both require a valid JWT, so this is not an open door. But a session-minting endpoint in a production project is a standing risk with no production purpose. Delete both before launch. They are trivially redeployable when needed.

For completeness, the two functions with `verify_jwt: false` are `staff-login` and `pin-login`. That is correct and intentional — they are the unauthenticated entry points, and both have their own rate limiting.

### F6 — MEDIUM: quotation links never expire

`get_quotation_by_token` and `accept_quotation` both match on token alone:

```sql
-- accept_quotation, in full:
update public.quotations
   set status='accepted', accepted_at=now(), accepted_by_name=p_signature_name
 where token = p_token and status <> 'accepted' and deleted_at is null;
```

There is no `expires_at` check anywhere in the quotation path. Compare `public_get_signature_request`, which correctly checks `expires_at`, `signed_at`, and `status`.

Consequence: a quotation link shared today is still live and acceptable a year from now, at a price that no longer applies. The `status <> 'accepted'` guard prevents double-acceptance but does nothing about staleness. Signature requests use a consistent 14-day TTL across all 13 rows — quotations should match.

### F7 — MEDIUM: 14 SECURITY DEFINER views

These views enforce the **creator's** permissions, not the querying user's, which means they can bypass RLS:

`dashboard_kpis_view`, `attendance_view`, `advances_view`, `trips_view`, `reminders_view`, `lead_source_performance_view`, `customer_360_view`, `trial_balance_view`, `gstr1_b2c_view`, `itc_register_view`, `fleet_compliance_view`, `trip_pnl_view`

Two more were reported by the linter beyond this list. Each needs review: does it filter on `org_id in (select current_org_ids())` internally? If not, it is a cross-tenant read path that sidesteps every restrictive policy you wrote. `customer_360_view` and `trial_balance_view` are the ones to check first — they carry the most sensitive data.

### F8 — MEDIUM: trigger functions exposed as REST endpoints

These are trigger bodies, not APIs, but PostgREST exposes them at `/rest/v1/rpc/…` to `anon`:

`enforce_order_limit`, `enforce_staff_limit`, `enforce_branch_limit`, `enforce_org_writable`, `notify_new_lead`, `notify_supervisor_assigned`, `sync_order_paid_total`, `org_members_hash_pin`, `assign_default_trial_plan`

Calling a trigger function outside trigger context generally errors, so exploitability is low. But they are surface area with zero purpose. `REVOKE EXECUTE … FROM anon, authenticated` on all nine.

**Verified NOT vulnerable** — two functions the linter flags that are actually defended in-body:

- `set_staff_pin` — guards on `is_org_owner(org_id) OR auth.uid() = staff.auth_user_id`, raises on failure. Anon cannot pass either branch.
- `get_org_owner_email` — guards on `is_platform_admin()`, raises otherwise.

Both are correct. Do not "fix" them.

### F10 / F11 — LOW

- 14 functions carry a mutable `search_path`, including `next_doc_number`, `amount_in_words`, `next_lr_number`, `norm_phone`, `current_fy_ist`. Low risk given they are not SECURITY DEFINER, but `SET search_path` is a one-line addition each.
- Auth leaked-password protection (HaveIBeenPwned check) is disabled. One toggle in the dashboard. Worth enabling before you have paying tenants.

## 4. Operational finding

### F9 — MEDIUM: the migration ledger does not reflect reality

| Metric | Value |
|---|---|
| Tables in `public` | 128 |
| Rows in `supabase_migrations.schema_migrations` | **2** |
| Version range | `20260816122528` – `20260816122744` |

The schema was built by pasting SQL into the dashboard, which is a reasonable workflow for a solo build and consistent with your rule that you run all SQL personally. The cost is that **the database cannot currently be rebuilt from source.**

Concrete consequences:
- No staging environment can be provisioned to match production
- A new tenant region, or disaster recovery, means hand-reconstruction
- The 128-table schema exists in exactly one place, with no reproducible definition

This does not require abandoning your workflow. It requires that migration files, once you have run them, get committed and recorded. A one-time `supabase db pull` would capture current state as a baseline going forward.

## 8. Assessment

The security architecture is genuinely good. 128 of 128 tables with RLS, 120 of 120 tenant tables covered, zero unprotected tenant data, and a provable demonstration that anonymous access is blocked while the intended resolvers work. That is a stronger foundation than most products have at launch, and it reflects the RLS work done over the previous sessions.

The failures in this report share one shape: **things that were built, then partly superseded, without the earlier version being removed.** Two function generations. Pages deployed from an untracked upload. A schema with no migration ledger. QA scaffolding left running. None of these is a design error — each is an artifact of moving fast across many sessions, which is the right trade for a solo build.

The correction is not more caution during the build. It is a deletion discipline: when a replacement lands, the thing it replaced gets dropped in the same commit. Every finding in §3 above would have been prevented by that one rule.

The customer-facing public pages are the weakest surface in the product right now, and they are also the only surface your tenants' *customers* will ever touch. Worth their own hardening pass before launch rather than being folded into the general module work.
